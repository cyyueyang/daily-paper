## 1. 项目概述

### 1.1 一句话描述

一个跑在本地 Mac/PC 上的 Python 服务：每天定时从 arXiv 抓取指定方向的最新论文，调用 DeepSeek API 生成中文速读卡片，通过飞书自建机器人推送给用户；用户回复「下一条」逐篇阅读，回复「详细」获取单篇深度解读。

### 1.2 目标

- 每天花 5–10 分钟即可刷完当日关注方向的 arXiv 新论文
- 两级阅读：速读卡片（轻）→ 深度解读（按需，省 token）
- 零服务器成本：本地常驻运行，飞书 WebSocket 长连接，无需公网 IP

### 1.3 非目标（明确不做）

- ❌ 不支持个人微信（无官方 API，封号风险）
- ❌ 不做 Web UI / 管理后台
- ❌ 不做多用户、权限系统（单用户个人工具）
- ❌ 不做论文全文翻译、PDF 下载管理
- ❌ 不做向量检索 / RAG 问答（v2 候选）

## 2. 用户与核心流程

### 2.1 用户画像

单一用户（项目所有者本人），关注方向：**LLM、具身智能（Embodied AI）、世界模型（World Models）、强化学习（RL）**。

### 2.2 每日核心流程（Happy Path）

```javascript
[每天 08:00 定时任务]
  1. 抓取 arXiv 昨日新论文（cs.CL / cs.LG / cs.AI / cs.RO）
  2. 关键词过滤 + 去重（已入库的跳过）
  3. 对入选论文逐篇调用 DeepSeek 生成「速读卡片」，状态记为 pending
  4. 向用户飞书推送一条汇总消息：
     「📄 今日新论文 8 篇（LLM×4, 具身×2, 世界模型×1, RL×1），回复「开始」或「下一条」开刷」

[用户阅读]
  5. 用户回复「下一条」→ 机器人发送最早一篇 pending 论文的速读卡片，状态记为 delivered
  6. 用户对某篇回复「详细」→ 抓取该论文 PDF 全文（失败则回退用摘要）→ DeepSeek 生成深度解读 → 发送，状态记为 read
  7. 用户回复「跳过」→ 当前篇标记 skipped，自动发下一篇
  8. 全部读完 → 发送「🎉 今日队列已清空」
```

## 3. 功能需求

### FR-1 arXiv 抓取

- 使用 arXiv 官方 API：`http://export.arxiv.org/api/query`
- 抓取分类：`cs.CL`、`cs.LG`、`cs.AI`、`cs.RO`，按 `submittedDate` 取最近 1 天（首次运行取最近 3 天补数据）
- 每次请求间隔 ≥ 3 秒（遵守 arXiv rate limit）；用 `start` + `max_results` 分页把目标日期范围内的结果**全部抓完，不设条数上限**（单日超出 `max_results` 一页时继续翻页）
- 抓取字段：`arxiv_id`、`title`、`authors`、`abstract`、`primary_category`、`categories`、`published`、`pdf_url`、`abs_url`
- **去重**：以 `arxiv_id`（不含版本号，如 `2601.12345`）为唯一键；同一论文跨分类出现只入库一次；新版（v2+）不重复推送
- **关键词过滤**（命中 title 或 abstract，大小写不敏感，可在 config 中增删）：
- 核心命中词（直接入选）：`large language model`、`LLM`、`embodied`、`world model`、`reinforcement learning`、`RLHF`、`reasoning`、`agent`、`robot learning`、`VLA`、`vision-language-action`、`diffusion policy`、`MCTS`、`in-context learning`
- 分类白名单内但未命中关键词的论文：不入主队列，写入 `papers` 表但 `filtered_out=1`（保留数据，便于以后调关键词）

### FR-2 DeepSeek 速读卡片生成

- API：DeepSeek 官方 API（`https://api.deepseek.com`），OpenAI 兼容协议，使用 `openai` Python SDK
- 模型：`deepseek-chat`
- 输入：论文标题 + 摘要
- 输出：严格按 5.3 节 Prompt 模板，生成中文速读卡片
- 失败重试：指数退避，最多 3 次；仍失败则该篇标记 `summarize_failed`，不阻塞其他论文
- 成本控制：速读卡片 `max_tokens=600`；单篇失败即跳过，不设全局熔断
- **每日生成篇数不设上限**：命中关键词多少篇就生成多少篇；多篇时逐篇串行调用、每篇间隔 ≥ 0.5 秒，避免触发 DeepSeek API 限流

### FR-3 本地队列与状态机

- 存储：SQLite，单文件 `papers.db`，用 SQLAlchemy 或 sqlite3 均可（推荐 SQLAlchemy）
- 论文状态机：

```javascript
  pending → delivered → read
               ↓          ↑
            skipped ──────┘  （skipped 的论文回复「详细」仍可深读）
  summarize_failed（终态，不进入推送队列）
```

- 「下一条」语义：取状态为 `pending` 中 `published` 最早的一篇；若无 pending，返回队列已清空提示
- 「当前篇」指针：用户最近一次收到卡片的论文记为 current，「详细」「跳过」「收藏」均作用于 current

### FR-4 飞书推送与交互

- 形态：飞书**自建应用机器人**（企业内应用即可，个人开发者创建免费）
- 连接方式：**lark-oapi Python SDK 的 WebSocket 长连接模式**（`lark.Client` + `ws.Client`），不依赖公网回调地址
- 需要的事件订阅：`im.message.receive_v1`（接收消息事件）
- 需要的权限 scope：
- `im:message`（读取消息）
- `im:message:send_as_bot`（发送消息）
- 推送内容均使用**飞书卡片消息（interactive card）**，卡片 JSON 结构见 5.4 节
- 用户身份校验：只响应 config 中配置的 `owner_open_id`，其他用户消息静默忽略（防误触）

### FR-5 交互指令集

| 指令（支持大小写、前后空格容错） | 行为 |
| --- | --- |
| `开始` / `下一条` / `next` / `n` | 发送下一篇 pending 论文速读卡片 |
| `详细` / `detail` / `d` | 对 current 论文生成并发送深度解读（调用 FR-6） |
| `跳过` / `skip` / `s` | current 标记 skipped，自动发送下一篇 |
| `收藏` / `star` / `fav` | current 标记 `starred=1`，回复「⭐ 已收藏」 |
| `列表` / `list` / `ls` | 发送今日队列概览：序号+标题+状态 emoji（⏳pending / ✅read / ⏭skipped / ⭐starred） |
| `统计` / `stats` | 发送累计统计：总抓取数、已读数、收藏数、DeepSeek 累计消耗 token 数 |
| `帮助` / `help` / `?` | 发送指令说明卡片 |
| 其他任意文本 | 回复「未识别指令，回复「帮助」查看可用指令」 |

### FR-6 深度解读

- 触发：「详细」指令
- 流程：

1. 下载论文 PDF（`pdf_url`，存 `data/pdfs/{arxiv_id}.pdf`，已存在则复用）
2. 提取全文文本（推荐 `pypdf`；提取失败或文本 < 2000 字符 → 回退仅用 abstract，并在解读开头注明「⚠️ 全文获取失败，本解读基于摘要」）
3. 全文超过 100k 字符时截断保留前 60k + 后 20k（保住方法/实验与结论）
4. 调用 DeepSeek（`deepseek-chat`，`max_tokens=2000`）按 5.5 节模板生成深度解读

- 深度解读结果入库缓存（`detail_text` 字段），重复请求直接返回缓存，不重复调用 API
- 解读较长时按飞书单条消息限制（约 4000 字符）分片发送，或改用「发送后追加」策略，由 agent 选简单方案

### FR-7 定时任务

- 使用 `APScheduler`（BlockingScheduler 与飞书 WebSocket 分线程运行）或系统 cron 触发 CLI 子命令，agent 二选一，**推荐 APScheduler 内嵌**，保证单一进程常驻
- 每日任务：config 可配，默认 `08:00`，执行 FR-1 → FR-2 → 推送汇总消息
- 进程崩溃恢复：重启后定时任务正常重新注册，队列状态从 SQLite 恢复（状态全在 DB，无内存态）

### FR-8 CLI 管理命令

除飞书交互外，提供命令行入口便于调试：

```bash
python -m paperbot fetch      # 手动执行一次抓取+总结（不入定时）
python -m paperbot push       # 手动推送今日汇总
python -m paperbot next       # 在终端打印下一条速读卡片（调试 DeepSeek 输出用）
python -m paperbot serve      # 启动常驻服务（定时任务 + 飞书长连接）
python -m paperbot stats      # 打印统计
```

### 5.3 速读卡片 Prompt 模板（写入 `llm.py`，不得改动措辞意图）

```javascript
你是一位资深 AI 研究员，擅长用中文一句话讲清论文核心。请基于以下论文信息输出速读卡片，严格遵守输出格式，不要输出任何额外内容。

标题：{title}
摘要：{abstract}

输出格式（Markdown）：
**{中文标题（自行翻译，忠实原意）}**
{英文原标题}

🏷️ 方向：{从 LLM / 具身智能 / 世界模型 / RL / 其他 中选一个}
💡 一句话核心：{≤50字，讲清这篇论文做了什么、解决了什么}
🔧 方法要点：{≤60字}
✨ 亮点：{≤40字，相比已有工作的差异}
📖 值不值得深读：{值得 / 扫一眼即可 / 可跳过}——{≤25字理由}
```

### 5.4 飞书卡片消息结构

速读卡片用飞书 interactive card：

- header：`{方向emoji} {中文标题}`，模板色按方向区分（LLM=blue，具身=green，世界模型=purple，RL=orange，其他=grey）
- body：卡片正文（5.3 输出内容）+ 一行小字 `作者：{前3位作者} et al. ｜ {published} ｜ {primary_category}`
- 底部 action 区放 3 个按钮（按钮回调等价于文字指令，降低打字成本）：
- `📖 详细` → 等价「详细」
- `⏭️ 跳过` → 等价「跳过」
- `⭐ 收藏` → 等价「收藏」
- 附一行纯文本链接：`🔗 abs 页面`（`abs_url`）

按钮回调需额外订阅 `card.action.trigger` 事件并在长连接中注册处理器；若实现成本过高，**允许降级为纯文字指令**（在卡片末尾提示「回复 详细 / 跳过 / 收藏」），但代码结构上要保留回调入口的扩展位。

### 5.5 深度解读 Prompt 模板

```javascript
你是一位资深 AI 研究员。请基于以下论文{全文/摘要}，用中文输出深度解读，面向有 ML 基础的读者，严格遵守格式。

标题：{title}
{full_text_or_abstract}

输出格式（Markdown）：
## 研究问题
{2-3 句：这篇论文要解决什么问题，为什么重要}
## 核心方法
{分点，3-5 条：方法的关键设计，必要时写出关键公式/模块名}
## 实验与结果
{2-4 句：在什么 benchmark 上、对比哪些 baseline、提升多少；数字必须来自原文，不得编造}
## 局限与开放问题
{1-3 条}
## 与相关工作的关系
{1-2 句：属于哪条技术路线，和哪些知名工作同谱系}
## 一句话总结
{≤40字}
```

### 5.6 每日汇总消息模板

```javascript
📄 arXiv 日报 · {date}
今日新增 {n} 篇（{方向分布，如：LLM×4 · 具身×2 · 世界模型×1 · RL×1}）
{前 3 篇标题列表，各带一行 matched_keyword 标签}
回复「开始」逐篇速读 ｜ 回复「列表」看全部
```

若当日 0 篇新论文，发送：「😴 今日 arXiv 无符合关注方向的新论文」。

## 6. 错误处理与边界情况

| 场景 | 期望行为 |
| --- | --- |
| arXiv API 超时/返回非 200 | 重试 2 次（间隔 5s），仍失败记日志并跳过本次抓取，不影响已入库队列 |
| 当日无新论文 | 正常推送「无新论文」消息，不报错 |
| DeepSeek API 报错/超时 | 单篇重试 3 次（指数退避 2s/4s/8s），失败标记 `summarize_failed` 继续下一篇；汇总消息中注明「{k} 篇总结失败」 |
| 飞书发送失败 | 重试 2 次，记日志；队列状态不前进（下次「下一条」重发同一篇） |
| 用户连发多条「下一条」 | 队列指针原子前进，不得重复发同一篇（DB 事务内更新状态） |
| 单日命中篇数异常多（如周一累积三天量） | 不截断、不丢弃，全部入队；汇总消息如实显示篇数；DeepSeek 调用按 FR-2 串行+间隔执行，允许整个生成流程跑较久（≥10 分钟不视为异常） |
| PDF 下载失败 / 解析为空 | 回退摘要解读 + 警告文案（见 FR-6） |
| 进程重启 | 从 SQLite 恢复全部状态，不丢队列、不重复推送当日汇总（用 `last_digest_date` 判重） |
| token 用量 | 每次调用记录 `usage.total_tokens` 到 papers 行与 state 累计值 |

## 7. 验收标准（code agent 完成后必须逐项自验）

1. `python -m paperbot fetch` 首次运行：能从 arXiv 抓到 ≥1 篇近 3 天论文，关键词过滤生效，`papers.db` 数据正确
2. 重复执行 `fetch`：无重复入库（arxiv_id 去重生效）
3. `python -m paperbot next`：终端输出格式符合 5.3 的速读卡片
4. 飞书侧：`serve` 启动后，向机器人发「下一条」→ 10 秒内收到卡片消息；发「跳过」「列表」「统计」「帮助」行为均符合 FR-5 表格
5. 发「详细」→ 收到含 5.5 全部六个小节的深度解读；第二次发「详细」命中缓存（日志无新 API 调用）
6. 非 owner 账号发消息：无任何响应
7. 手动杀掉进程重启：状态无损，当日汇总不重复推送
8. 定时任务：将 `DAILY_PUSH_TIME` 设为当前时间 +2 分钟，到点能收到汇总消息
9. 密钥全部来自 `.env`，仓库中无明文密钥；提供 `.env.example`
10. README 包含：飞书自建应用创建步骤（含所需权限 scope 清单）、DeepSeek 充值入口、安装运行命令

## 9. 参考实现与复用策略（重要：不要从零造轮子）

GitHub 上已有高度相似的开源实现。**实现策略：先通读参考仓库对应模块的代码，在此基础上按本 spec 的增量需求改造，而非从零编写。**

### 9.1 主要参考：elena-daily-paper-scout

- 仓库：`https://github.com/Win7win/elena-daily-paper-scout`
- 与本项目的重合度最高，以下模块**直接参考其代码实现**：
- 飞书自建应用 WebSocket 长连接接入与 `card.action.trigger` 按钮回调派发（对应其 `core/feishu_app.py`、`core/card_actions.py`）——覆盖本 spec 的 FR-4
- 「精吃」异步深读链路：PDF 下载 → 解析 → LLM 分析 → 结果回推（对应其 `skills/arxiv_eater/`）——覆盖本 spec 的 FR-6，注意其 PDF 解析默认依赖 MinerU，**本项目按 FR-6 使用 pypdf 即可，不引入 MinerU**
- 卡片按钮 `value` 字段的 action 派发设计模式（`deep_eat`/`up_vote`/`down_vote` → 本项目的 `detail`/`skip`/`star`）
- 调试脚本思路（`scripts/get_chat_id.py` 获取 chat_id / open_id 的方式可照抄）
- 已知坑（其 README 明示，实现时注意规避）：
- arXiv 官方接口偶尔返回 429，需加重试与代理支持（本项目 config 增加可选 `HTTP_PROXY` 项）
- 飞书卡片模板需在飞书卡片搭建台导入发版；**本项目改用代码内直接构造 interactive card JSON，不走卡片模板平台**（减少配置步骤，见 5.4 节）

### 9.2 次要参考：arxiv_daily_paper_push

- 仓库：`https://github.com/NN0202/arxiv_daily_paper_push`
- 参考价值：DeepSeek 结构化中文解读的 prompt 组织方式、飞书富文本卡片的排版样式（供 5.4 节卡片设计参考）
- 注意：该项目是群 webhook 单向推送、无交互、无状态存储，**架构不可照搬**，仅参考其内容生成层

### 9.3 本 spec 的增量需求（参考仓库均未覆盖，需全新实现）

以下是本项目与所有现成仓库的差异化功能，是 code agent 的主要新增工作量：

1. **pending 阅读队列 + 状态机**（FR-3）：现成项目都是"一次推一摞"，没有逐篇推送的队列语义
2. **「下一条 / 跳过 / current 指针」文字指令集**（FR-5）：现成项目只有按钮反馈，没有会话式指令
3. **SQLite 持久化 + 崩溃恢复**（FR-3、FR-7）：elena 用 JSON 文件存储，本项目要求 SQLite + 完整状态机
4. **owner 身份校验**（FR-4）：只响应单一用户

### 9.4 复用时的约束

- 参考代码的许可证需兼容（elena 与 arxiv_daily_paper_push 均为公开仓库，引用其代码片段时保留出处注释）
- 复用代码必须适配本 spec 的配置体系（`.env` + pydantic-settings）和目录结构（第 4 节），不得原样拷贝其配置读取方式
- 无论参考多少，**第 7 节验收标准不变**，全部必须自验通过

## 11. 已知风险与备注

- arXiv API 偶发慢响应，抓取总耗时应容忍到 2 分钟
- 每日篇数无上限意味着 token 成本随当日篇数线性浮动（周一补量时可能 30+ 篇），属预期行为；通过「统计」指令可监控累计消耗
- `deepseek-chat` 上下文 128k，FR-6 的截断策略已留足余量，无需升级模型
- 飞书长连接模式断线会自动重连（SDK 内置），无需自行实现
- v2 候选（本次不做，但 schema 不阻拦）：星标论文导出、周报聚合、按星标训练关键词权重、Telegram 通道
